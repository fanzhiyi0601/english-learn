# Design

## Context

全新空项目（当前仅有 PyCharm 示例 main.py），从零搭建一个面向 6 岁孩子的纯前端英语启蒙网页。动机见 proposal.md - Why。范围为展示型"看 + 听"功能，并带简单的练习问答与金币奖励。技术约束：仅用浏览器内置能力，无第三方依赖、无后端。

## Goals / Non-Goals

**Goals:**
- 零依赖、纯静态的网页应用，双击即可本地运行
- 3 个并列展示模块（字母/单词/句子）+ 首页导航
- 发音完全依赖浏览器内置 Web Speech API（SpeechSynthesis）TTS
- 简单选择题问答 + 答对金币动画 + 累计计数（localStorage 持久化）

**Non-Goals:**
- 不引入前端框架（React/Vue 等）、不引入运行时构建工具、不引入后端（Vitest 仅作开发期测试依赖）
- 不做复杂题型（仅单向选择题，不做听写/填空/跟读）
- 不做语音评测、账号系统、家长后台、云端同步

## Decisions

### 决策 1：单文件或极简静态结构
- **选择**：一个 HTML + 分离的 CSS/JS 文件，纯静态。
- **理由**：内容量小、无状态、无需构建，符合"最基本功能"。
- **备选**：单文件内联所有内容——更少文件但难维护；多页面——增加导航复杂度，对幼儿交互不友好。故采用单页应用式切换（SPA 风格，用 JS 切换视图而非多 HTML 页）。

### 决策 2：发音用浏览器 TTS
- **选择**：Web Speech API 的 `window.speechSynthesis` + `SpeechSynthesisUtterance`，语言设为 en-US/en-GB，matched to 英文发音。
- **理由**：零依赖、无需准备音频资源。权衡：音质和口音取决于系统/浏览器自带声音，可能不够地道、无真人感。
- **备选**：真人录音音频文件（音质好但需资源）、第三方 TTS SDK（需要网络/密钥）。因范围最小且离线可用，选浏览器内置。

### 决策 3：内容用 JS 数据对象驱动渲染
- **选择**：把字母、单词、句子内容定义为前端 JS 常量数据（数组/对象），由渲染逻辑统一生成卡片，避免重复 HTML。
- **理由**：便于后续增删内容，结构清晰。卡片点击统一绑定 TTS 播放逻辑。练习题目也由同一份数据生成，保证展示与问答一致。

### 决策 4：幼儿友好交互
- **选择**：大号触控目标、全屏卡片网格、点击即发音（无需二次确认）、显著返回按钮。
- **理由**：目标用户是自主操作的 6 岁孩子，交互必须极简、反馈即时。

### 决策 5：练习题为单向选择题
- **选择**：每个模块提供选择题（如 "读出 X，请选出对应项"），选项从同模块数据中随机取若干，正确答案随机分布。
- **入口**：每个模块视图内嵌一个醒目的"练习"按钮，点击进入该模块的问答模式；问答结束后可返回该模块展示页。
- **理由**：对 6 岁孩子双向选择题最简单，无需键盘输入，点击即可作答。
- **备选**：听写/填空/跟读——需要更多交互与较难的正误判断。v1 排除。

### 决策 6：金币动画用纯 CSS/JS
- **选择**：答对时在卡片位置生成金币 DOM 元素，用 CSS 动画做弹出/飞散（偏移、旋转、淡出），结束后移除。
- **理由**：无需图片/精灵资源，自包含、轻量。每次答对固定 +1 金币。

### 决策 7：金币计数用 localStorage
- **选择**：累计金币数存于 `localStorage`（如 key=`coinCount`），页面加载时读取，答对时写入。
- **理由**：无需数据库，浏览器本地即可跨刷新保留。权衡：本地存储不清除则永久保留，且无法跨设备同步（非目标）。

### 决策 8：单元测试覆盖每个模块，用 Node 测试框架
- **选择**：每个模块的开发均配套单元测试，测试全部通过才视为该模块成功完成；任一测试失败则需修改直到通过。测试框架选用 **Node 测试框架（Vitest）**，作为 npm 开发依赖引入。
- 说明：核心逻辑（数据完整性、TTS 封装、选择题生成与正误判断、金币计数与 localStorage 读写）抽成可测的纯函数，供 Vitest 断言；DOM 交互与动画副作用最小化。运行时保持零依赖，测试依赖（Vitest）仅存在于开发期，不打包进交付页面。
- 范围：字母、单词、句子、语音合成、练习问答、金币等模块的纯逻辑均需测试覆盖。**首页导航与幼儿友好样式组不强制单测**——其主体为大 DOM 布局/样式/跳转副作用，适合浏览器手动走查而非纯函数断言，故该组任务不附带单元测试要求。
- 验收门槛：tasks.md 中每个模块任务在其勾选描述里写明"且对应单元测试通过"作为完成条件。

### 决策 9：内容来源与产出
- **选择**：v1 的字母示例、单词、句子内容由实现阶段直接生成并硬编码在前端数据文件中；后续接入后端能力时改为从接口获取，数据结构保持兼容。
- **理由**：当前无后端，先保证内容可用、结构清晰；数据驱动结构（决策 3）为未来接后端预留了替换点。

## Risks / Trade-offs

- [TTS 发音质量不稳定，随浏览器/系统声音变化] → 接受为 v1 权衡；若需更高音质，后续可换真人录音（属内容层替换，不影响整体架构）。
- [TTS 在部分浏览器/平台不被支持] → 做能力检测，不支持时降级为纯展示，不报错打断（已在 spec 中体现）。
- [图片资源可能缺失] → v1 采用 emoji 或简单 CSS 绘图代替真实图片，减少资源准备成本。
- [题目随机可能偶然重复或选项过简单] → 从数据池随机取选项并打乱，保证至少 3-4 个选项、正确答案位置随机。
- [localStorage 可能被清空或不可用] → 读不到时回退为零，不影响展示功能。
- [纯静态零依赖与单元测试存在张力] → 运行时保持零依赖、双击可跑；Vitest 仅作为开发期 npm 依赖用于跑测试，不打包进交付页面。
- [浏览器环境难以在纯 JS 测试中直接验证 DOM/TTS/动画] → 将这些逻辑抽为纯函数单独测试，交互类副作用由浏览器手动走查覆盖，避免强依赖 DOM 的脆断测试。
